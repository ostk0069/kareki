kareki は Dart / Flutter のワークスペース内の参照をたどり、使用が確認できないコードを検出します。名前が同じでも、宣言ごとに区別して解析します。

## 解析の流れ

1. `melos.yaml`、pub workspace、または設定からパッケージを検出します。
2. Dart のソース、宣言、抑制コメントを収集します。
3. 呼び出し元がなくても使用中とみなすコードを、解析の起点にします。
4. analyzer で参照先を解決し、起点から参照をたどります。
5. 到達できない宣言、参照されていないファイル、宣言されているものの使用が確認できない pub 依存パッケージを報告します。

`--packages` などのパッケージ指定は、報告する範囲だけを絞ります。ソースの収集先やパッケージの探索設定については、[設定](configuration.ja.md)を参照してください。

## 解析の起点

次の 4 つを解析の起点として使います。

| 種類 | 例 |
|---|---|
| Dart / Flutter の規約 | トップレベルの `main`、テストファイル、`bin/`、`integration_test/`、`lib/l10n/`、`flutter_test_config.dart`。 |
| 設定 | `entry_points.files` と `entry_points.names`。デフォルトのファイル指定は stories と widgetbook に対応します。 |
| アノテーション | 組み込み・独自のプリセットと、`keep_alive_annotations.custom`。 |
| 生成ファイル・除外ファイル | 未使用として報告しない場合も、その宣言と参照先を解析に含めます。 |

生成コードからの参照も考慮するため、生成元の宣言の誤検出を抑えられます。解析前にコード生成を実行してください。kareki 自体は不足しているファイルを生成しません。

## 同名宣言と省略可能な引数

参照先は名前だけでなく、個々の宣言に対応付けます。`A.load()` が使われていても、それだけで無関係な `B.load()` を使用中とはみなしません。ただし、明示的な `entry_points.names` の指定は名前で照合します。

省略可能な引数は、生成コードや到達できないコードも含む、収集した全ソースの呼び出しから使用状況を調べます。実際のオーバーライドやリダイレクトファクトリの関係も考慮し、引数ごとに次の状態を区別します。

| 状態 | 意味 |
|---|---|
| 使用確認済み | 既知の呼び出しで値が渡されているか、対応する解析モデルで使用の可能性が確認できたため、残す必要があります。 |
| 解析範囲内で未指定 | 調べた呼び出しで値が渡されておらず、不明な呼び出し経路も残っていません。指摘の対象になります。 |
| 不明 | 安全に確認できない呼び出し経路があります。未使用とは判定しません。 |

正規のトップレベル `main` の位置引数は、実行環境から渡される場合があります。ただし、関数本体で使っていない引数を検出する別のルールからは除外しません。

## 解析で保証できないこと

動的な呼び出し、コールバック、条件付き import などでは、使用状況が確定しない場合があります。kareki は使用の可能性があるコードを残し、必要に応じて解析警告を出します。解析警告は未使用コードの指摘とは別です。出力先と終了コードは [CLI リファレンス](cli.ja.md)を参照してください。

指摘は、解析したソースとビルド構成に対するものです。ワークスペース外のアプリケーションによる public API の利用や、全プラットフォームでの実行結果までは保証しません。ビルド前にソースを差し替える場合は、各構成の準備後に解析するか、入口となるファイルを明示的に残してください。kareki は差し替えスクリプトを実行しません。

削除前に指摘と警告を確認し、削除後にはコード生成、静的解析、テスト、必要なビルドを実行してください。

## 対応バージョン

| コンポーネント | バージョン |
|---|---|
| Dart SDK | `>=3.10.0 <4.0.0` |
| analyzer | `>=10.2.0 <15.0.0` |

CI では、対応するすべての Dart マイナーバージョンと、最新の安定版 SDK で解析とテストを実行します。

具体的な解析手順と、判断が難しいコード例は[解析の内部仕様](analysis-internals.ja.md)を参照してください。
