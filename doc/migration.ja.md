---
title: 名前ベースの解析からの移行
weight: 8
---

次のリリースでは旧方式を撤去し、到達判定と任意引数の呼出状況を、analyzerで
解決した宣言IDだけで判断します。名前ベースの方式へのフォールバックはありません。

1. 対象プロジェクトのSDKで依存解決と通常のコード生成を実行してください。
   生成・除外ファイルも参照元になるため、参照解決できる状態が必要です。
2. 設定の `analysis_mode` とスクリプトの `--analysis-mode` を削除してください。
   残っている場合は、黙って無視せず終了コード64で移行を案内します。
3. baselineを更新する前に検出差分を確認してください。保存ID・JSON形式は維持しますが、
   同名宣言を区別できるため新たな検出が増えることがあります。
   パッケージ絞り込みは報告範囲の指定であり、参照元を切り捨てません。
4. API呼出には `await` が必要です。`KarekiRunner` / `DoctorRunner` の `run()` と
   `analyze()`、CLIの `runCli()` / `runDoctor()` は非同期です。
   プレビューの `runCliAsync` / `runDoctorAsync` と `AnalysisMode` は撤去します。
   `ParsedFile` / `DeclarationRecord` / `EntryPointSet` の旧方式専用の名前参照情報も撤去します。
5. 抑制の整理前に `kareki doctor` を実行してください。参照解決は１回だけ行い、
   各チェックで共有します。安全に整理できない警告が残る場合は終了コード2です。

参照解決に失敗した場合、グラフを使う解析は部分的な結果を公開せず中止し、baselineも
上書きしません。不確実性の警告は未使用の指摘とは異なり、保守的な保持を継続します。
グラフ不要のルールは依存解決なしでも実行できます。永続キャッシュは使用せず、
次回の実行では現在のソースを再確認します。

新方式は名前照合より時間・メモリを必要とします。計測ツールの引数は `ROOT [doctor]`
です。同一SDK・同一ソース・同一設定・同一ルールを、別プロセスで複数回測定し、
最大RSSも確認してください。ソース変更の影響とエンジンの性能差は分けて評価します。
